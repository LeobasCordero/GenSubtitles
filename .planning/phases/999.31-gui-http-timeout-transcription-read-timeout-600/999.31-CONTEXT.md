# Phase 999.31 — BUG: GUI Transcription HTTP Timeout

## Problem Statement

`HTTPConnectionPool(host='127.0.0.1', port=8000): Read timed out. (read timeout=600)`
appears in the GUI when transcription of a long video/audio exceeds 600 seconds.

## Root Cause (confirmed by codebase analysis)

`_run_step_in_bg` in `gensubtitles/gui/main.py` (line ~610) uses:

```python
resp = req.post(f"{server.BASE_URL}{api_endpoint}", json=payload, timeout=600)
```

The flat `timeout=600` applies to **both** the connect timeout and the read timeout.
The `/steps/transcribe` endpoint runs synchronously (blocks until Whisper finishes).
For long videos with slow models, transcription easily exceeds 600 seconds → the
`requests` read timeout fires and raises `ReadTimeout`, which propagates as an exception
and is logged as the error seen by the user.

## What Is NOT Affected

- **Tab 1 "Generate Subtitles"** — uses `_run_sse_flow` which already sets
  `timeout=(5, None)` on the SSE stream (connect timeout 5 s, read timeout unbounded).
  This path is correct and unaffected.
- **Tab 2 "Translate Subtitles"** — calls `translate_file()` directly in Python,
  no HTTP request; no timeout issue.

## Affected Code Path

| Tab | Handler | HTTP Call | Current Timeout | Risk |
|-----|---------|-----------|-----------------|------|
| 3 Extract | `_on_tab3_extract` | POST /steps/extract | 600 s flat | Low (fast) |
| **4 Transcribe** | `_on_tab4_transcribe` | POST /steps/transcribe | **600 s flat** | **HIGH** |
| 5 Translate | `_on_tab5_translate` | POST /steps/translate | 600 s flat | Medium |
| 6 Write SRT | `_on_tab6_write` | POST /steps/write | 600 s flat | Low (fast) |

All four step-tabs share the same `_run_step_in_bg` method, so all are affected by
the same timeout.

## Decisions

### D-01 — Fix timeout in `_run_step_in_bg`
Change `timeout=600` → `timeout=(5, None)`.
- Connect timeout (5 s): catches "server not running" errors quickly
- Read timeout (`None`): allows transcription to run as long as needed
This mirrors the pattern already used by `_run_sse_flow`.

### D-02 — No changes to error handling
The existing exception handler in `_run_step_in_bg` already calls `on_error(str(exc))`,
which routes to the tab's log textbox. After the fix, genuine failures (server down,
model error) will still surface correctly. No changes needed.

### D-03 — No migration of step tabs to SSE
The step-tab API calls are already async from the GUI's perspective (run in a daemon
thread). The server-side is synchronous by design. Converting to SSE would be a
separate, larger change and is out of scope for this bug fix.

## Deferred Ideas

- SSE/streaming progress for stepper tabs (out of scope — separate phase if desired)
- Per-model timeout hints or UI indication that long transcription is expected

## Fix Summary

**One-line change** in `gensubtitles/gui/main.py`:

```python
# Before
resp = req.post(f"{server.BASE_URL}{api_endpoint}", json=payload, timeout=600)

# After
resp = req.post(f"{server.BASE_URL}{api_endpoint}", json=payload, timeout=(5, None))
```

File: `gensubtitles/gui/main.py`, method `_run_step_in_bg`, inside `_worker()`.
